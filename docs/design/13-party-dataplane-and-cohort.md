## 1. 核查背景与判定标准

现状:本服组队链路(建队 CMD 12、邀请 CMD 10、接受 CMD 11、退队 CMD 13、踢人 CMD 14、转让 CMD 131,下行 NOTI 6/7/8/9/10/11/26)均有实现与自测覆盖,真机复测统一归 `PENDING.md` P-36;参考服 ACT12_Server 在同机双开场景下组队可用。

本文档把"组队可用"拆成可判定的四段,后续核查与实施均按此口径:

| 段 | 判定标准 | 现状 |
| --- | --- | --- |
| A 建队与名册 | 邀请弹窗出现、接受后双方名册一致、队长权柄正确 | 建队与邀请已通(真机);**接受步失败**,定位与首批容错见 §11 |
| B 城镇互见与门口准入 | 同队成员在城镇同一区域内互相可见;全员通过门口"场景检查"(客户端串 0x215 不弹) | 同区域互见已通(真机,§11);跨区域不可见(§4 G-4) |
| C 同副本运行 | 队长选图后**全员**进入同一副本实例、同房间、同怪物与同结算 | **未实现**(§4 G-1) |
| D 副本内实时同步 | 队员位置/动作经 UDP 互通;服务端侧数据报归属与转发正确 | 形态与参考不同(§4 G-2/G-3),C 未落地前不可判定 |

## 2. 参考服 ACT12 的整体设计(可用形态)

### 2.1 监听面与端口

| 面 | 参考服 ACT12 | 依据 |
| --- | --- | --- |
| 入口 TCP | `config.Port`(默认 7001),接受频道选择与登录 | `server_config.h:11`、`server_core.cpp:22` |
| 频道 TCP | 每频道一个监听器,端口由系统分配(`Start(host, 0)`)后回填 `PublishChannelPorts` | `server_core.cpp:40-55` |
| 频道信息的端点下发 | 频道信息包携带**通告主机串**(`AdvertisedHost`)+ **NAT 探测主/次端口** | `proto/session_packets.cpp:5-26` |
| NAT 探测 UDP | 单进程双 socket,主/次两端口(默认 606 / 562),`SO_EXCLUSIVEADDRUSE` + 非阻塞 + 独立线程 | `net/nat_probe.cpp:5-42`、`server_config.h:12` |
| TCP 中继(P2P 兜底) | 独立 TCP 监听(默认 5555),随登录应答下发 `relay host / tcp port / udp port` | `net/peer_relay.cpp:53-75`、`proto/session_packets.cpp:28-54` |

要点:**UDP 侧只有 NAT 探测一个监听面**,参考服不存在"玩法数据报中继"。落在 5555 的是 **TCP** 中继(帧头 `type/len/source/target`,转发时把 `type` 改写为 3 后投递,见 `net/peer_relay.cpp:124-171`),供客户端在无法直连时使用;它按账号注册(登录时 `Relay().Admit(accountId)` 授租约,`handlers/account.cpp:38`)。

### 2.2 NAT 发现阶段(服务端侧)

| 项 | 参考服行为 | 依据 |
| --- | --- | --- |
| 请求校验 | `length != 1` 或首字节不是 1/5 一律丢弃 | `net/nat_probe.cpp:80` |
| 限流 | 按源 IP 32 次/秒,全局 256 次/秒窗口计数 | `net/nat_probe.cpp:72-84` |
| 回包 | 7 字节 `{2, 公网 IP(4B,主机序整型值按小端写出,如 127.0.0.1 → 01 00 00 7F), 公网端口(LE)}`,发回探测源 | `net/nat_probe.cpp:85-92` |
| 首字节 5 的回包端口 | **由对侧端口发出**(`sender = request[0] == 5 ? 1 - i : i`),即源过滤行为测试 | `net/nat_probe.cpp:90` |
| keepalive | 10 字节(首字节 0),客户端每 10s 发往次端口;服务端不识别该长度,按非法请求丢弃 | `net/nat_probe.cpp:78-81` |

客户端侧分类(本仓库 IDA 结论,`client-function-register-60cn.md` §10):state1 值 1 发主端口 → 载荷 IP 等于本机假定 IP 记 type 1;state2 值 1 发次端口 → 端点与 state1 相同进 state3、不同记 type 3;state3 值 5 发主端口 → 有回包记 type 2、无回包或坏包记 type 4;state4 每 10s 发 10 字节 keepalive。回包**只校验首字节 == 2**,`recvfrom` 源地址不参与比对。

### 2.3 端点上报(SET_IP,对应本客户端 CMD 2)与校验

参考服从 TCP 对端地址 + 报文正文读出 `PeerAddress`,校验后才落到在场连接态:

| 校验 | 条件 | 依据 |
| --- | --- | --- |
| 最低长度 | 正文 ≥ 19 字节 | `net/peer_address.h:20` |
| 尾部形态 | `u32 长度 ≤ 64`,正文 = 19 + 长度(或 16 字节对齐补零后等长),补零段必须全 0 | `net/peer_address.h:21-25` |
| 字段合法性 | `nat ∈ 1..4`、内网/公网 IP 非 0、端口非 0、`MTU ∈ 576..65507` | `net/peer_address.h:10,31-32` |
| 公网 IP 一致性 | 上报公网 IP 必须等于 TCP 连接的对端 IP | `net/peer_address.h:31` |

处理链(`handlers/peer_network.cpp:32-56`):回 `CommandOk` → `Town().UpdateNetwork(连接, 地址)`(`session/town_presence.cpp:387-394`,同一地址重复上报直接返回不触发) → `Parties().RefreshNetwork()` + `Pvp().RefreshNetwork()` 重发端点表。即**上报值写进在场状态,端点表由在场快照现场生成**。

### 2.4 组队域(注册表、发布模式、端点表)

- 结构:固定 4 槽(`std::array<weak_ptr<Connection>,4>`),`PartyIdentity{队伍号, 队长角色号, 频道, 深渊进度}` 作为**一代标识**,`m_membership` 角色→队伍号(`session/party_registry.h:8-17,43-48`)。
- 邀请三分支与 30s 过期:发起者已有队(须为队长且未满)→ 受邀请者入队;受邀请者已有队 → 发起者申请加入;双方无队 → 新建并以发起者为队长(`session/party_registry.cpp:159-230、127-134`)。
- 目标定位用 `LookupChannel`(**同频道且双方都在城**,`session/town_presence.cpp:283-294`),而非同区域。
- 发布模式(`Publish`,`session/party_registry.cpp:43-96`):

| mode | 载荷 | 发送时机 |
| --- | --- | --- |
| 0 | 设置段 + 名册段 + 端点表 | 建队、接受成立新队 |
| 1 | 仅设置段 | 改队名/容量 |
| 2 | 名册段 + 端点表 | 加入既有队、退队/踢人/转让后的刷新 |
| 3 | 空载荷(清空 4 槽) | 解散 |

  另:mode != 3 时对每个成员先各自重播其身份包(NOTI 2,正文取在场快照的 `State.Identity`,该处 `ProtocolId = 2`),使各成员客户端刷新对端上下文。
- 端点表(`SendNetwork` + `BuildPeerAddresses`,`session/party_registry.cpp:98-115`、`proto/peer_packets.h:5-17`):逐成员取在场快照,`Network.Valid()` 才收录(要求 nat 1..4、内外网 IP 与端口、MTU 全非零),记录 = `{u16 角色, u32 内网 IP, u32 外网 IP, u16 端口, u32 账号, u8 nat, u32 MTU, u8 体力}`;**记录塞的是队员自己上报的真实端点**;一条都凑不出时**整个包不发**(`proto/peer_packets.h:12`)。只收录与队伍同频道的成员,目标成员不在场时该目标不发(`session/party_registry.cpp:105-108`)。

结论:参考服的队员记录是"真实端点直连形态",服务端**不参与玩法数据报的搬运**;因而参考服不需要"按源端点归属发送者"这一机制。

### 2.6 数据面归属与兜底

- 副本内成员位置/动作:客户端之间的**直连 UDP**,目标地址来自 NOTI 11 的真实端点;服务端不搬运。
- 客户端收包归属键是**帧内槽位字节**(本仓库 IDA 结论,`client-function-register-60cn.md` §4):类型 1/2 取偏移 7、类型 0 取偏移 1,槽位越界或无对端对象即整包丢弃,源 ip:port 只用于类型 2 的地址学习。
- 直连不可用时改走 5555 的 **TCP 中继**(参考服只提供通道与租约,由客户端自行决定是否改走;登录应答下发 relay 端点是该通道的入口)。

### 3.2 NAT 探测(已按 10 号文档加固的形态)

- 长度 == 1 且值为 1/5 才回包(7 字节 `{2, 公网 IP, 端口}`),**保持同 socket 回包**;keepalive(10 字节首字节 0)只观测不计回包;按源 IP 固定窗口限流(默认 32 次/秒,双端口共用);计数器 + 5 秒聚合日志(`Network/Protocol/GameDatagramProtocol.cs:68-96`、`Network/GameplayDatagramService.cs:307-387`、`docs/design/10-udp-nat-dataplane.md` §4.3/§4.4)。

### 3.3 端点上报与解析(自报 / 认领 / 解析三字段)

- CMD 2 解析 `GameNatReport{nat, 内网 IP, 公网 IP, 公网端口, MTU}`(正文偏移 2 起 15 字节,端口按**大端**读),写入在场连接态;解析端点按总序四级决定:认领端点 > 非共享 IP 的观测端点 > 自报公网端点 > 无(`Network/Protocol/GameDatagramProtocol.cs:49-66`、`Network/GameplayDatagramService.cs:571-670`)。
- 上报后立即重发全队端点表(`Network/Handlers/Login/SetUdpEndpointHandler.cs:28-37` → `PartyCoordinator.RefreshPartyEndpoints`)。

### 3.4 组队域

- `PartyManager`:4 槽、邀请/接受/退队/踢人/转让、断线清理;与参考服的**有意差异**:队长退队时退役旧队伍号并重建(本客户端把 NOTI 9 type 0 当作按槽位的**有序差分**,复用旧号会损坏名册),断线保留代号与槽位(`Game/Party/PartyManager.cs:627-708`)。
- `PartyCoordinator`:成队时按"详情 → 端点表 → NOTI 8 → 名册 → 端点表 → NOTI 26"顺序下发(抓包结论,勿照搬参考顺序);成员互发 NOTI 2 mode 3 详情快照以创建对端对象(`Network/PartyCoordinator.cs:246-264,450-467`)。
- **端点表的形态与参考服相反**(`Network/PartyCoordinator.cs:477-514`):**除接收者自己的记录外,其余队员一律填服务端自身监听端点**(内网/公网 IP 同值 = `GameplayDatagram.Host`,端口 = 主端口),自报值只用于本人记录;即"全队只与服务端对话,由服务端转发"。

### 3.5 副本(单人)

- 选图与进图按**单会话**处理:布局生成、掉落计划、结算基数一律 `partyMemberCount: 1`(`Network/Handlers/Dungeon/SelectDungeonHandler.cs:201-210`、`Network/Handlers/Dungeon/DieMonsterHandler.cs:234`、`Network/Handlers/Dungeon/SetPlayResultHandler.cs:88,165`)。
- 选图阶段下发的是**单人**端点表(1 条本人记录)与 NOTI 26(默认槽位 0)(`Network/Handlers/Dungeon/StartGameHandler.cs:64-85`)。
- CMD 40 无队伍屏障,单会话即提交并回 NOTI 30(`Network/Handlers/Dungeon/FinishLoadingHandler.cs`)。
- 进副本**不撤出**城镇在场表(`TownPresenceService.RemovePresence` 仅被会话关闭路径调用,`Network/TownPresenceService.cs:500-523`)。

### 3.6 数据面(服务端中继)

- 客户端玩法数据报的**唯一去处**是 NOTI 11 通告的服务端端点;服务端按**到达源端点**反查会话,经队伍名册转发给同队其他成员的解析端点(接收循环同步归属 + 逐对端异步发送;含块结构门、槽位观测、聚合计数)(`Network/GameplayDatagramService.cs:431-534`、`docs/design/10-udp-nat-dataplane.md` §4.5)。

## 4. 逐项对照:缺口与判定

| 编号 | 维度 | 参考服 | 本项目 | 判定 |
| --- | --- | --- | --- | --- |
| G-1 | 组队副本协同 | 队长选图拉全员入同一实例,共享运行态 + 加载屏障 + 事件队列 | 无;副本单人,`partyMemberCount: 1` | ❌ 阻断 |

| G-8 | P2P 兜底通道 | 5555 TCP 中继(登录应答下发端点) | 无;本客户端是否存在同类通道尚未取证 | ⚠️ 待核验 |

### G-1 组队副本协同缺失(阻断)

- **依据**:本客户端只由队长发起门口命令——`sub_8779F0` 选图确认流仅在"该槽成员 == 自己"时发 CMD 15,**"非队长等服务器拉入"**(`docs/protocol/client-function-register-60cn.md` §6);门口场景检查(0x89F560 一带)只负责"全员通过才发 CMD 15 + 对每个对端对象发起 P2P 握手",不含任何拉人语义。参考服正是用 `BeginSelection` + `sendPartyDungeon` 承接该职责(`session/party_registry.cpp:457-497`、`session/party_dungeon.cpp:35-93`)。
- **本项目现状**:CMD 15/16 全链按单会话处理,除队长外的成员**收不到任何进图包**,停留在城镇;副本内共享击杀/结算/加载屏障均无。因此"两人组队后一起打副本"这一组队的主要用途在本服不可能达成,表现为"队伍建得起来但用不了"。
- **同时对数据面的影响**:客户端的 P2P 握手只在**副本门口**发起(城镇不发任何数据报,已由双端实测与反汇双重确证,`docs/protocol/packet-detail-party-60cn.md`「前置」节)。协同未落地前,D 段(副本内同步)在真机上根本不会被走到——**G-2/G-3 的判定必须排在本项之后**。
- **对齐方向**:按参考形态的自有实现(非字节照搬):成员快照校验(一代标识 + 连接 + 在场状态一致性)→ 选图阶段全员下发(NOTI 3 全员状态行 / 每人 NOTI 2 详情 / NOTI 26 / NOTI 27 / 可选提示)→ 进图阶段全员校验与收费、房间按实际人数生成、逐成员投递入场包 → 共享运行态(世界态 + 加载屏障 + 逐成员事件队列)→ 撤离统一回城。落点建议:`Game/Party/PartyRun.cs`(共享运行态)、`Network/PartyDungeonCoordinator.cs`(快照/投递/屏障编排),`SelectDungeonHandler`/`StartGameHandler`/`FinishLoadingHandler`/`DieMonsterHandler`/`SetPlayResultHandler` 改为经协调器取队伍上下文;`partyMemberCount` 由人数真值驱动。新增目录/文件按 07 §4.8.3 映射表先登记再落地(B1)。

### G-2 端点表语义:真实端点直连 vs 服务端端点中继(高危)

- **依据**:参考服 `BuildPeerAddresses` 逐成员取在场快照的真实 `PeerAddress`(`proto/peer_packets.h:5-17`),`SET_IP → UpdateNetwork → RefreshNetwork` 是该表的唯一刷新源(`handlers/peer_network.cpp:32-56`)。
- **本项目**:为规避"客户端间直连常被对方防火墙拦截"而改为全队统一通告服务端端点并由服务端转发(`Network/PartyCoordinator.cs:477-514`、`docs/protocol/packet-detail-party-60cn.md`「服务器中继」)。
- **判定**:两条路线在协议上都"能被客户端接受"(客户端收包按帧内槽位归属、源 ip:port 仅作学习量),但**代价不同**:中继路线把"发送者归属"从客户端挪到服务端,引入了参考服完全没有的依赖(G-3);直连路线则与参考服同形态,风险与参考服一致(跨 NAT 可能不通,但同机/同网段可用)。
- **对齐方向(二选一,待定)**:路线 A 直连优先(端点表改回真实端点,保留中继为可选兜底);路线 B 维持中继(需要 G-3 成立 + 归属加固,并把"跨 NAT 可用"作为本服相对参考服的增益)。决策所需判据见 §7。

### G-3 中继归属前提(高危,待真机判定)

- **依赖**:中继按 `_sessionsByEndpoint`(解析端点)反查发送者(`Network/GameplayDatagramService.cs:438-448`),而解析端点来自**探测/保活**的观测端点;只有当客户端的**玩法数据报源端点**与探测/保活源端点一致时,反查才成立。
- **已知风险**:
  - 客户端的 NAT 发现模块(socket `this+12`)与 MT-UDP 核心(`NUDPCore`,0xD01D00,独立收包线程)可能是**不同的 socket**;若不一致,玩法数据报的源端口与观测端点不同,反查全部落空(聚合行 `unattributed` 持续增长),中继静默失效。反证:参考服的真实端点直连形态能工作,说明"上报端点 = 玩法 socket 端点"在 A12 代成立;本代客户端需以日志判定。
  - 同 IP 多会话的认领缺口(ADD-06/P-19)已按 `docs/design/10-udp-nat-dataplane.md` §4.2 收口,但它的前提同样是"观测端点可与自报端点精确匹配";若 CMD 2 的端口字节序与实现不符(本客户端写入点申报为"主机序",本服按大端读),精确匹配会恒不命中并持续计入 `claimSkipped`。该项一次抓包即可定论(见 §7 诊断清单 D-4)。
- **对齐方向**:先判定后决策。若反查成立且 `unattributed` 恒零,路线 B 可行;若反查落空,则必须改路线 A(或改为按 IP 扇出/按会话槽位归属等替代归属键,均属客户端可见行为或状态面改动,须另行设计)。

### G-4 在场可见范围与邀请可达性(中)

- **参考服**:入城/切区时向**同频道**所有会话交换身份包(NOTI 2)与状态(NOTI 3),只有**同区域**才追加 NOTI 23 与 AREA_USERS 成员表(`session/town_presence.cpp:134-185`);组队邀请用 `LookupChannel`(同频道 + 双方在城)。
- **本项目**:外观包与 USER_AREA 只在**同区域 + 同频道**之间交换(`Network/TownPresenceService.cs:319-378,567-586`)。
- **后果**:本客户端 NOTI 7 的接收端要求 uid 能在本地城镇用户表中命中(命中失败静默丢弃,`docs/protocol/packet-detail-party-60cn.md` NOTI 7 节),因此**跨区域邀请实际不可用**(服务端允许,客户端无记录可渲染弹窗);同时组队窗口的成员/目标列表也只看得到同区域玩家。
- **对齐方向**:身份包交换范围放宽到"同频道"(位置/区域仍按区域级),使跨区域邀请与组队列表恢复;属客户端可见行为变更,须列入真机验收。

### G-5 进副本不撤出城镇可见集合(中)

- **参考服**:选图阶段对全员 `EnterDungeon`,离城即向同频道他人撤下可见性(`LeaveLocked` + NOTI 6/23),并给自己补一条 NOTI 23(area=255)(`session/town_presence.cpp:81-96`)。
- **本项目**:进副本不动在场表,同区域其他玩家仍能看到该角色立在门口,直到回城刷新(`Network/TownPresenceService.cs:500-523` 仅会话关闭路径调用)。
- **对齐方向**:并入 G-1 的实施批次,按参考形态在进图投递时撤出可见集合并补自身区域过渡包;验收判据:双客户端同区域,一人进副本后另一人应看到其从场景消失。

### G-6 选图阶段的房主槽位与端点表形态(中)

- **房主槽位**:本项目在 CMD 15 时下发 NOTI 26 使用的是**默认槽位 0**(`Network/Handlers/Dungeon/StartGameHandler.cs:80` 调用 `CreateUdpHost()` 无参),而车队路径用的是真实槽位(`Network/PartyCoordinator.cs:524` → `party.LeaderSlot`)。本服支持 CMD 131 转让队长且**不压缩槽位**(`Game/Party/PartyState.cs:188` 取成员实际槽位),转让后队长可在 1..3 槽;此时选图阶段的 NOTI 26 槽位与名册尾字节不一致——客户端以 NOTI 26 槽位启动对端数据报路径,槽位错即数据报路径指向错误对端。参考服在同一位置用 `HostSlot()` 真值(`handlers/dungeon_selection.cpp:126-127,206`)。属可确证的实现缺陷,随 P1 一并修正。
- **端点表条数**:选图阶段只发 1 条本人记录。按 IDA 结论,NOTI 11 接收端逐记录更新、无清表分支(`docs/protocol/packet-detail-party-60cn.md` NOTI 11 节),故不构成缺陷;仍建议随 P1 改为"全队表 + 真房主槽位",与参考形态一致并消除覆盖风险。

### G-7 通告地址一致性(中,配置面)

参考服只有 `AdvertisedHost`(+可选 `RelayHost`)一处通告地址,同时用于频道信息与 NAT 探测端口下发(`proto/session_packets.cpp:5-26,28-54`)。本项目 `Channel.Host`(TCP 通告)与 `GameplayDatagram.Host`(UDP 通告)各自独立:非本机部署时若只改前者,通告给客户端的探测/中继地址仍是回环地址,远端客户端会探测自身而失败。验收/加固方向:部署侧同一地址两处同时配置,并在启动日志中并列打印两个通告地址以便核对(不改协议字节)。

### G-8 P2P 兜底通道(待核验)

参考服的 TCP 中继是 A12 代客户端可用的兜底(登录应答携带 relay host/tcp/udp 端口)。本客户端(60A1)的登录应答为固定 5 字节、不含端点字段,且本仓库既有取证未登记任何中继 socket 或族;`ENUM_CMDPACKET_REPORT_BAD_P2P_USER`(CMD 52)存在于枚举表但未实现(`docs/protocol/client-packet-enums-60cn.md`)。结论:本客户端是否存在同类通道**尚未取证**,按 D1 不猜测。若不存在,数据面只能依赖 UDP(路线 A 或 B),G-2 的决策权重上升;若存在而未实现,则需另行补齐并纳入真机窗口。

## 5. 不构成缺口的形态差异(避免误对齐)

- **探测字节 5 的回包端口**:参考服从对侧端口回包(`net/nat_probe.cpp:90`),本项目保持同 socket 回包。逐字段核对后确认**不构成功能差异**:两方案的回包载荷完全一致(公网 IP + 客户端源端口),而客户端只校验首字节 == 2、不比对源地址(`client-function-register-60cn.md` §10),分类结果(state3 有回包 → type 2)也不变;反向差异(NAT 仅放行最近一次目的端口)只会让参考形态更严、本形态更宽,不是可用性风险。维持 `docs/design/10-udp-nat-dataplane.md` §3 的非目标结论,不改。
- **名册换代 / 字段位宽 / 对端上下文形态**:队长退队换代并重建(参考服就地换代)、NOTI 10 的 uid 为单字节、NOTI 9 设置段 kind==0 携带 dstr、用 NOTI 2 mode 3 而非参考服的身份包重播——均为本客户端已取证的世代差异(`docs/protocol/packet-detail-party-60cn.md` 各节【差异】标注),**不可按参考服"对齐"**;组队下行顺序(详情 → 端点表 → NOTI 8 → 名册 → 端点表 → NOTI 26)同样以本服抓包结论为准。
- **NOTI 3 的载荷形态**:参考服的选图广播是"1 字节行数 + N 行 `{u16 角色, u8 状态}`"的单包多行形态(`session/party_registry.cpp:481-483`);本客户端 NOTI 3 恒为 3 字节单行 `{u16 uid, u8 state}`(`docs/protocol/packet-detail-misc-60cn.md` NOTI 3 节,构建器 `CharactersPacketBuilders.CreateUserState`)。组队场景须按"每个成员的下行各自成包"实现,不得照搬参考的单包多行载荷(照搬会在本客户端上错位)。

## 9. 风险与回退

- **P1 触及副本主链**(选图/进图/加载/结算均为已真机验证路径):按"单会话行为等价"托底——单人进副本的包序、字节与判定必须与实施前逐字节一致;任一步不成立即整体回退该阶段,不设运行期开关。
- **共享运行态的并发**:成员掉线/断线重连/队长转让与事件队列消费交叉,按参考服的"运行态加锁 + 逐成员队列"形态实现,并补自测覆盖;不做无锁化探索。
- **P2 若改路线 A**(端点表改真实端点):属客户端可见行为变更,须先经 IDA 复核 NOTI 11 记录用途 + 双客户端真机验证(含 3 人以上与跨网段场景),失败即回退路线 B 的现形态。
- **G-4 的可见性放宽**:可能让玩家在城镇看到更多远端角色(不同区域),若出现客户端性能或场景异常,按区域回退。

## 12. 设计审查(2026-10-08,客户端 IDA 复核后重审)

本节按"设计假设是否成立"逐项重审 UDP/NAT/组队三面,证据均为 2026-10-08 对客户端主程序(60A1,ImageBase 0x400000)的 IDA 复核结论。

### 12.1 数据面拓扑:现有设计的核心假设不成立(需重做)

| 项 | 客户端实际行为(IDA) | 本项目现状 | 判定 |
| --- | --- | --- | --- |
| 玩法数据报的目标选择 | 发送函数 `sub_907160` 按对端对象的 `+0x2C` 字节二选一:`== 0` → `sendto(对端记录 IP(+0x1C), 端口(+0x20))`;**`!= 0` → 套上 12 字节帧头 `{u16 type, u16 len, u32 源账号, u32 目标账号}` 交给 TCP 中继传输对象**(`vtable+260`) | 假设"客户端必然往 NOTI 11 通告的端点发 UDP",据此实现服务端 UDP 中继 | **不成立**:通告端点只在 `+0x2C == 0` 时才被使用 |
| 中继开关的来源 | 对端对象由 48 字节描述符队列喂入(`sub_908340` 消费 → `sub_907AE0` 建对象,`a6` 写 `+0x2C`);描述符字段 = `{动作, 主机名串, 端口, 槽位, 账号, +0x2C 字节}` | 全队通告 `nat = 上报值(1..4)` 或默认 `2`(均非 0) | 若 `+0x2C` 即记录 `nat` 字节,则**本服通告值使客户端一律走中继**;两者关系尚待定案(见 §12.6) |
| 中继通道配置 | **登录应答下发**:CMD 1 应答 case(0x40F2E0)读 `u8 result + u8×4 + u32 账号(写 dword_B55EE0 = 中继帧源账号) + dstr 中继主机(cap 0x10) + u32 端口1 + u32 端口2 + u8×2`,再调 `sub_906070(中继传输, host, port1, port2)`(置使能位 +2556、strncpy 主机、写两端口) | 登录应答固定 5 字节 `[1,0,0,0,0]`,**不含账号/主机/端口** | **缺陷**:客户端读完 5 字节后继续读 23+L 字节,中继配置与账号全为越包尾的残留值 |
| 中继帧头 | 与参考服 `net/peer_relay.cpp` 读的 `{type,len,source,target}` 逐字段同构;中继按**账号**寻址(目标账号来自对端记录 `+0x28` = NOTI 11 的 accId) | 无 TCP 中继 | 参考服的 5555 中继即此通道的服务端;`accId` 字段是它的寻址键 |

**结论**:现有"服务端 UDP 中继 + 全队通告服务端端点"的拓扑,**前提是客户端会往通告端点发 UDP**,而客户端实际还有一条由登录应答配置、按账号寻址的 TCP 中继通道,且其选择由对端对象的 `+0x2C` 决定。因此必须二选一重做:

- **路线 A(推荐先行,改动最小)**:通告 `nat = 0`,使客户端走直连 UDP 分支(目标 = 我们通告的服务端端点),现有 UDP 中继即可承载组队数据报;需验证客户端对 `nat == 0` 无其他副作用(已知唯一额外消费点是"Relay"状态标注,见 §12.2)。
- **路线 B(对齐原服,跨 NAT 的正解)**:补全登录应答的中继字段 + 实现按账号转发的 TCP 中继(帧头 `{type,len,source,target}`,转发时把 type 改写后投递),使客户端的中继通道可用;这是参考服"能组队"的实际承载路径。

### 12.2 中继开关的语义已确证:客户端会把它标注为 "Relay"

开关查询 `sub_907DF0(槽位)` 返回 `peer->+0x2C != 0`,唯一消费点在 `sub_832F60`(0x8330CA):为真时在成员状态叠加层里打印字面量 **`"Relay"`**(受调试开关 `byte_BEE776` 控制)。即:客户端自身把"走中继的对端"显式标注出来 —— 这同时给了真机判据:**组队后若队友旁出现 "Relay" 标注,即客户端选择了中继通道**(此时本服无中继可用,数据面必然不通)。

### 12.4 不合理之处的共同根因
